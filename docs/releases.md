# Releases

**CTL-2263 (2026-08-26): release-please is reinstated**, scoped to the plugins that survived the CTL-2218 cleanup. CTL-2220 (2026-08-26, earlier the same day) had removed it at Ryan's direct request; CTL-2262 reversed that decision and CTL-2263 restored it against the repo as it stands now — not a blind revert of CTL-2220, since five plugins and the packaging pipeline changed in between. See "Versioning" below for what runs today.

## Versioning

- A conventional-commit push to `main` triggers `.github/workflows/release-please.yml` (`googleapis/release-please-action@v5`), which opens or updates a single release PR covering the 5 surviving plugins (`release-please-config.json`'s `packages`, `separate-pull-requests: false`).
- Merging that PR bumps `version.txt` and both `plugin.json` files (`extra-files` in the config, one entry per manifest) per changed plugin, writes each `CHANGELOG.md`, tags `<component>-v<version>`, and publishes a GitHub Release per bumped component.
- There is no daily auto-merge cadence and no AI release-notes enhancer — both existed pre-CTL-2220 and neither was restored (see "What CTL-2263 deliberately did not restore" below). The release PR is merged like any other PR, by a human or by the fleet.
- `scripts/check-plugin-version.sh` (the `check-versions` required PR check) still runs, and its conventional-commit escape hatch is still correct — but the story behind it changed. A conventional-commit message makes the check pass **without** a hand version bump, and that is now right because release-please bumps the version after merge; it is not "nobody will bump this." If a plugin changed without its version changing and the branch's commits aren't conventional-commit-shaped, hand-bump `version.txt` and both `plugin.json` files in the same PR — but a hand bump alongside a conventional commit is a double bump, so don't do both.
- `scripts/packaging/cli.mjs render --write` (the vendor-neutral packaging pipeline — see `docs/specs/accepted/vendor-neutral-packaging/spec.md`) still never writes a version itself: its Claude emitter copies `$.version` verbatim from the existing file, and its Codex emitter seeds from the Claude manifest on create and fails on regenerate if the two disagree. That makes release-please's `extra-files` write a **fixed point** for the render — re-rendering after a release PR reproduces exactly what release-please wrote, so `packaging-gate.yml`'s drift check stays green.
- `scripts/check-plugin-manifest-parity.sh` (the `check-plugin-manifest-parity` required-adjacent PR check) still runs on every PR. Beyond its original three checks (Claude/Codex `plugin.json` version parity, no stray `version` in either marketplace catalog), CTL-2263 added a fourth: every `release-please-config.json` package entry must carry the full release-please schema (`release-type`, `component`, `changelog-path`, `include-component-in-tag`) and a complete `extra-files` pair pointing at both `plugin.json` files. This closes a hole CTL-2220 left when it deleted `validate-release-config.sh` and replaced only that script's Checks 9–11 — nothing asserted `extra-files` actually pointed at real files, and the failure mode was silent (`version.txt` bumped, both `plugin.json` files left behind).

## What CTL-2263 deliberately did not restore

Each of these existed before CTL-2220 removed them; none was brought back, and each is a separable feature rather than part of "conventional commits cut releases":

- **The AI release-notes enhancer** — the pre-removal workflow's second job, running `scripts/enhance-release-notes.sh` against `ANTHROPIC_API_KEY` per release. Reinstating it means resurrecting ~400 lines and a per-release model spend for a feature nobody asked back.
- **The daily auto-merge cadence** — a scheduled workflow that merged the release PR at 05:00 UTC. ADR-009 (below) marked that design Superseded; reinstating releases does not require reinstating a robot that merges them.
- **The release-health check** — a scheduled probe that filed a GitHub issue against a human's queue on failure. Paging a human directly is exactly what AGENTS.md's escalation rule prohibits; if release-pipeline health needs watching, it belongs in the Loki alert path.
- **`validate-release-config.sh` as a standalone script (11 checks)** — the one check from that set the current gates genuinely lacked (extra-files completeness) was folded into `check-plugin-manifest-parity.sh` instead; the rest are covered elsewhere or no longer apply.

## Plugin version-bump collision policy (CTL-2266)

A plain `git merge` cannot see one collision class: two PRs independently bumping the SAME plugin to the SAME target version (e.g. both `12.66.3` → `13.0.0`) merge cleanly — no conflict marker, no red check — because git sees both sides making the identical change. Only a *different* target produces a real conflict, which `check-plugin-version.sh` and the catalyst-cloud-proven Mergify merge queue's built-in `-conflict` guard already surface. This policy, and the guard below, close the silent case.

- **The queue owns rebasing; an author never pre-emptively re-bumps.** A PR is submitted (and labelled `queue:ready`) with whatever version it derived from the main it branched from.
- **On a dequeue for a real conflict, the dequeued lane re-bumps.** It rebases onto the new main and **re-derives** the target version from main's *current* value — never a raw merge that preserves the stale number, and never `--theirs`/`--ours` on `version.txt`. Re-derivation, not reconciliation.
- **`check-plugin-version.sh` asserts monotonicity.** For every plugin whose `version.txt` changed relative to `$BASE_REF`, the PR's value must be strictly greater (semver-compared) than `$BASE_REF`'s current value, and both `plugin.json` files must carry that same value. Because a merge queue re-runs required checks against the current base on every requeue, this fires on the queue branch — catching the identical-target (or now-stale-lower-target) collision before merge, which a raw git merge alone cannot. An unreadable base value (e.g. a brand-new plugin with no history at `$BASE_REF`) fails closed rather than passing as "no collision".
- **Interaction with a possible release-please return (CTL-2263).** If release-please is reinstated, it owns bumps via release PRs and feature PRs stop bumping by hand, which dissolves this collision class — but introduces a different one: merging a `release-please--branches--main` PR cuts a GitHub Release, and `publish-skills.yml` triggers on `release: published`, pushing to the sibling repo `coalesce-labs/catalyst-skills` with a scoped token. That is outward-facing and must never be an unattended queue merge — a merge-queue config for this repo excludes `release-please--*` head branches by name for exactly this reason, so this policy holds correct under both futures.

## Version Source of Truth

| File | Purpose | Updated By |
|---|---|---|
| `plugins/<x>/version.txt` | Canonical version | release-please (`extra-files` in `release-please-config.json`), on merge of the release PR |
| `plugins/<x>/.claude-plugin/plugin.json` | Plugin version — gate for Claude Code auto-updates | release-please (`extra-files`) |
| `plugins/<x>/.codex-plugin/plugin.json` | Codex plugin version (CTL-1463) | release-please (`extra-files`), kept in sync with the Claude manifest by `cli.mjs`'s regenerate-time equality check and `check-plugin-manifest-parity.sh`'s PR-time check |
| `plugins/<x>/CHANGELOG.md` | Per-plugin changelog | release-please, on merge of the release PR |
| `.claude-plugin/marketplace.json` | Claude plugin registry (paths only, **no versions**) | Manual |
| `.agents/plugins/marketplace.json` | Codex plugin catalog (paths only, **no versions**) (CTL-1463) | Generated (`bun scripts/packaging/cli.mjs render --target codex --write`) |

The `version` field in `plugin.json` is the auto-update gate: at session start Claude Code fetches the marketplace repo, and if `plugin.json.version` at the new HEAD differs from the installed version, it refreshes the cache. Same version → skipped even if code changed.

`.codex-plugin/` and `.agents/plugins/` are **generated, gitattributes-marked** trees — never hand-edited — regenerated with `bun scripts/packaging/cli.mjs render --target <claude|codex|agentsSkills> --write`.

## Portable Skills Pack Publication (CTL-2215)

On a published GitHub Release, `.github/workflows/publish-skills.yml` regenerates the `agentsSkills` target, grades it against the agentskills.io/`skills`-CLI contract (`bun scripts/packaging/cli.mjs conformance --target agentsSkills`), and — if it changed — pushes the result into the sibling repo **`coalesce-labs/catalyst-skills`**, under `skills/`, as an ordinary accumulating commit on `main` (never a force-push, never a history rewrite). That repo is **generated and must never be hand-edited** — its own README says so in its first line. A byte-identical regeneration reports `no-change` and pushes nothing; a missing `SKILLS_PUBLISH_TOKEN` or an unresolvable target repo fails the job loudly rather than skipping. The `release: published` trigger is live again as of CTL-2263 (release-please, above, is what creates GitHub Releases); the workflow's `workflow_dispatch` trigger (with a `dry_run` input, default `true`) remains available for a manual publish or a dry-run rehearsal.

Each publish also pushes a lightweight tag mirroring the source release tag, so a consumer can pin by tag or by commit SHA — a `workflow_dispatch` run has no release tag to mirror and skips that step. **The pack SHA (the commit this workflow pushes to `coalesce-labs/catalyst-skills`) is the pinning unit** downstream consumers record — e.g. catalyst-cloud's runner-container image label (CTC-977/CTC-1034) — so a container build can always trace back to the exact source commit that produced the skills it shipped.

`separate-pull-requests: false` means one release-PR merge can publish up to 5 releases (one per bumped component) in the same batch — all rendering byte-identical pack content, since the pack isn't per-plugin. CTL-2263 hardened the workflow for that case: a workflow-level `concurrency` group (keyed to the workflow, not the ref) serializes the triggered runs instead of racing them, and tag mirroring is decoupled from the content-change decision — a release mirrors its tag whether or not it was the one release whose merge actually changed the pack (`no-change` releases mirror the tag alone; the one `publish` release pushes branch + tag atomically). Tag mirroring is idempotent and fail-closed: a tag already at the run's own SHA is a no-op; a tag at a different SHA fails loudly, naming both SHAs, rather than silently reassigning which pack content a consumer's pin resolves to.

**Known limitation — a multi-release batch can still drop the middle tags, and it needs one manual step.** GitHub's concurrency queue holds exactly one *pending* run per group, and `cancel-in-progress: false` only protects the run that is already executing: "any previously pending job or workflow in the concurrency group will be canceled." So when a merge publishes N releases at once, run 1 executes, runs 2..N-1 are each superseded while pending, and only run N survives — so releases in the middle of the batch reach no run and get no mirrored tag. The pack *content* is unaffected (all N render identically, and run 1 publishes it); only those tags are missing. **Recovery: re-run each cancelled run from the Actions tab.** That is exact, not approximate — the tag step is idempotent and fail-closed, so a re-run pushes only the missing tag and refuses rather than overwrites if a tag already points somewhere else. After any multi-component release, check that `coalesce-labs/catalyst-skills` carries one tag per release in the batch. A durable fix (a per-release concurrency group plus a rebase-and-retry on the branch push, so no run is ever superseded) is tracked as a follow-up rather than attempted here — it is new workflow logic that CI cannot exercise.

Install with `npx skills add coalesce-labs/catalyst-skills`.

The publish DECISION (no-change / publish / inconclusive) is a pure, unit-tested function (`scripts/packaging/publish/plan-publish.mjs`); git mechanics (clone/commit/push/tag) live in the workflow itself.

## Commit Conventions

Conventional-commit messages are required — release-please parses them to decide what to bump and what to write into each changelog, and `scripts/check-plugin-version.sh` looks for the same format as its pass-without-a-manual-bump escape hatch (see above). See `AGENTS.md` → "Commit Conventions" for the format and valid scopes.

## `release-please-config.json`

This file is release-please's config again. CTL-2220 had stripped it to a bare `{"packages": {"<plugin-dir>": {"component": "<name>"}}}` roster — no `$schema`, `release-type`, `changelog-path`, or `extra-files` — because two other consumers, `scripts/packaging/cli.mjs`'s `readConfigPackageOrder()` (plugin-render ordering) and `check-plugin-version.sh`/`check-plugin-manifest-parity.sh` (roster reads), already hardcoded this filename and neither was in that ticket's scope to re-point. CTL-2247 asked whether that coupling should be re-pointed or decoupled once release-please came back.

**CTL-2263 resolved CTL-2247: keep the coupling, deliberately.** Now that this file carries the real release-please schema again, `readConfigPackageOrder()` reading it for manifest-emission order is a legitimate consumer of the file that declares the plugin roster — not a repurposing that needs undoing. Renaming it now would mean editing four consumers (`cli.mjs`, `check-plugin-version.sh`, `check-plugin-manifest-parity.sh`, `catalyst-legacy-plugin.test.sh`) plus this runbook to *reduce* honesty about what the file is. It is also not a single point of failure for "which plugins exist": plugin *discovery* (`listPluginRelPaths()`) is disk-derived, and `assertPluginInventoryAgreement()` cross-checks it against this file's declared order in both directions, throwing a named error on disagreement either way — this file supplies order, not membership. See `readConfigPackageOrder()`'s doc comment in `scripts/packaging/cli.mjs` for the same decision recorded in code.

## Troubleshooting

The release workflow exists again (`.github/workflows/release-please.yml`) — if plugin files changed and the `check-versions` PR check fails, see "Versioning" above. If the `check-plugin-manifest-parity` check fails, it means either the Claude/Codex `plugin.json` versions (or a marketplace catalog's stray `version` field) actually disagree, or a `release-please-config.json` package entry is missing a required schema field or `extra-files` target — fix the value, this check does not auto-correct anything. There is still no scheduled release job and no release-health check (see "What CTL-2263 deliberately did not restore" above) — a stalled release PR or a failed release run needs a human or the fleet to notice it directly; nothing pages on it.
